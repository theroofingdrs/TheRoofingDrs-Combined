# Automatic website intake

All residential inspection/contact/estimate and commercial inspection/contact/emergency/calculator submissions now use the existing servers and the service-only `crm_receive_website_lead` RPC in Operations. The RPC creates the operational lead and its complete record graph transactionally. No public request can choose its authoritative division or use a service credential.

A browser submission key and immutable payload make retries safe after delayed or lost responses. The browser stores only a digest, UUID and initial attribution, not contact details. User-visible confirmation requires an actual delivered CRM receipt. Fields remain on errors. The calculator no longer displays success when its final submission failed. Contact pages have associated labels, autofill hints and mobile keyboard hints, and accept either a phone number or email without requiring a full property address for a callback.

Server prerequisites: `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, stored as encrypted runtime secrets/configuration. Never set the service key in a Vite variable. All new Operations migrations must be installed in the same Supabase project before this website release. A missing RPC/credential returns a visible error; there is no fallback that claims a local JSON write is CRM delivery.

Notification jobs commit with the lead, but the worker remains default-off pending provider/sender/account/scheduler approval. Booking remains disabled; its prepared engine is isolated from public routes. Confirmation pages do not promise dispatch, a booked appointment or an unverified response deadline.

Validation: `npm test`, `npm run test:mobile`, and the cross-repository Operations command `WEBSITE_SOURCE_DIR=<website checkout> python3 scripts/test-security.py intake`. The latter runs real website HTTP handlers and real SQL with a synthetic transport bridge; separate real PostgREST JWT tests prove service/browser authorization. No production inquiry or notification is generated by these tests.
